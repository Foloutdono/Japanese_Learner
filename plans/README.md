# Wave 3 — Sentence analysis (2026-08-26)

A **feature** wave, not an audit wave. Written from an approved design for
rethinking the phrase-analysis mode, plus a grilling pass that produced
`CONTEXT.md` (shared vocabulary) and six ADRs under `docs/adr/`. Planned at
commit `d4911a6`.

Everything above this line is the completed UI/UX work (plans 001-011). This
wave is independent of it.

## The idea in one paragraph

The phrase analyzer costs one LLM call per sentence and shows nothing without a
provider — while the backend already owns a morphological analyzer, a 205-point
levelled grammar catalogue, a JLPT difficulty grader and per-kanji furigana
alignment, none of which it uses. Everything except the contextual gloss and the
prose explanation is computable **locally, instantly, free**. Splitting analysis
into a local tier and a paid deep tier is what makes three new things
affordable: an analyzer that answers instantly, a photo of a page, and a
YouTube video's subtitles.

# Wave 4 — Making image and video actually work

Planned 2026-08-26 at commit `2552915`, from a live diagnosis rather than an
audit. Wave 3 shipped photo input and video subtitles; **both were unusable in
production**, reported as *"every link i try doesnt work, every picture return
either a complete mess of characters or wrongs ones."*

Four root causes, all confirmed live — none of them speculative:

| # | Symptom | Root cause | Plan |
|---|---|---|---|
| 1 | Render log full of tracebacks; every request slow | JWKS client points at `/auth/v1/jwks`, which **401s** (needs an `apikey` header PyJWKClient never sends). The public set is at `/auth/v1/.well-known/jwks.json`. Local JWT verification has **never worked**; every request pays two Supabase round trips | [021](021-supabase-jwks-endpoint.md) |
| 2 | White-screen `Cannot read properties of undefined (reading '0')` | `getExam` returns `{generating: true}` on a 202 — truthy, no `sections`. `ExamRunner` guards it; **`ExamResult` does not** and crashes on `exam?.sections[0]` | [022](022-exam-generating-shape-crash.md) |
| 3 | Photos return character soup | Tesseract.js on raw photographs, with no preprocessing and no crop. The vision tier meant to rescue it was never built, because **plan 018's probe was wrong** — NVIDIA's **free** API serves vision models that read this correctly | [023](023-vision-ocr-backend.md), [024](024-image-capture-ux.md) |
| 4 | Every YouTube link fails | Render is a datacenter; YouTube blocks datacenter IPs for caption endpoints. The code is **correct** — identical calls succeed from a residential IP | [025](025-paste-transcript-ingest.md), [026](026-youtube-url-honesty-and-proxy.md) |

## The two findings that reframe the wave

**Plan 018's vision probe produced a false negative.** It concluded *"No model
is confirmed vision-capable on either provider"* — but it only tested the seven
models already hardcoded in `_PROVIDER_CATALOG`, all of them text-only. It never
asked either provider which models accept images.

Re-probed 2026-08-26 with the keys already in `backend/.env`. **NVIDIA's free
API — the one this backend already uses for text — serves working vision
models.** Benchmarked on three Japanese images of increasing difficulty (clean;
rotated + noisy + blurred + JPEG-q32; vertical *tategaki*):

| Model (NVIDIA, free) | clean | hard horizontal | vertical |
|---|---|---|---|
| **`nvidia/nemotron-nano-12b-v2-vl`** | **3/3** | **2/2** | **3/3** |
| `nvidia/llama-3.1-nemotron-nano-vl-8b-v1` | 3/3 | 1/2 | 2/3 |
| `meta/llama-3.2-90b-vision-instruct` | 3/3 | 2/2 | 0/3 |

The winner **matches the paid OpenRouter models on every case** (controlled
against `qwen/qwen3-vl-30b-a3b-instruct` and `qwen/qwen2.5-vl-72b-instruct`,
both 3/3 on the same vertical image). It fails transiently about **1 call in 5**
but scores perfectly whenever it answers — which is what `chat()`'s existing
retry-and-fall-back chain is for.

Two things plan 018 got wrong, both worth remembering: a **429 is a quota
signal, not a capability signal**, and **vertical text is a prompt problem, not
a model problem** — every model scored 0/3 on *tategaki* until told to read
columns top-to-bottom, right-to-left, then 3/3.

**Only YouTube's caption *fetch* is blocked — the *player* is not.** The IFrame
API runs in the learner's own browser on their own IP and embeds fine.
`VideoPlayer.jsx` already works. So the missing piece is only caption *text*,
and the learner's browser already has it: YouTube's own "Show transcript" panel
is plain selectable text. Pasting it cannot be IP-blocked, needs no proxy or
key, works for any video they can watch, and lands in the same `Cue` shape as
the other two ingests — so nothing downstream changes. That is plan 025, and it
is the wave's most important plan.

## Cost: zero

**This wave adds no paid dependency.** Vision OCR runs on NVIDIA's free API,
the same account already serving the text models. Video needs no third party at
all — paste and upload are pure local parsing — and the proxy in plan 026 is
opt-in and off by default.

The constraint that replaces cost is **shared free quota**. NVIDIA's tier is
per-account, so OCR load competes with the analyzer's deep tier and exam
generation; heavy OCR use would show up as *those* features slowing or 429ing.
Plan 023 Step 5 therefore keeps a per-user daily cap (default 60 images/day) —
not to bound spending, but to stop one client degrading everything else.

Paid vision models are recorded in plan 023 (two verified OpenRouter ids, about
$0.0002/image) purely so the option is documented if a budget ever appears.
Nothing uses them, and an executor reaching for them is a named STOP condition.

## What this wave deliberately does not do

- **No YouTube cookies or account sessions.** Attaching a real person's
  logged-in identity to automated fetches is against YouTube's terms in a way
  the paste ingest is not, and it breaks constantly. Named as a STOP condition
  in plan 026.
- **No scraping of YouTube's markup.** That recreates exactly the coupling the
  paste ingest removes.
- **Tesseract is not deleted.** It stays as the offline/private option, which
  preserves what ADR-0004 originally chose to protect — now stated as a choice
  rather than as the only path.
- **No self-hosted ASR.** Unchanged from ADR-0003.

## Decisions this wave embodies

`CONTEXT.md` is the vocabulary these plans use. The key rename: **Sentence**
replaces **phrase** in all new code, while the existing `phrase_history` /
`phrase_analysis_cache` tables and `/api/phrase/*` routes keep their names,
because renaming them costs a migration and buys nothing visible.

## Live defects this wave fixes in passing

Found while planning, each confirmed against the code:

- **French users get English explanations.** `SYSTEM_PROMPT`
  (`backend/routes/phrase.py:30`) never receives the UI language. Fixed in 014.
- **Reopening a history entry shows stale SRS badges.** `phrase_history` freezes

## Traps worth knowing before you start

- **`analyze_local` must stay pure** — no database, no `user_id`, no `core/`
  imports. That is what lets one analysis be cached and shared across every
  learner. Per-user SRS state is attached separately, at read time.
- **Token offsets are load-bearing.** Four screens render highlights, ruby,
  click targets and cloze blanks from them. Plan 013's offset-contiguity test is
  the guard; an off-by-one there is a visible defect everywhere.
- **Off-deck is not unknown.** A word in no app deck (proper noun, JMdict-only,
  slang) is something the app cannot teach, not something the learner failed to
  learn. Counting the two together would make every photo and every video
  caption look impossible and would make the i+1 signal permanently false.
- **`add_app_cards` skips rather than errors**, by design
  (`backend/routes/decks.py:868`). It returns `{"added": n}` where `n` can be
  less than what was sent. Any UI on top of it must read the count.
- **A deck holds exactly one structure**, so mined vocab, kanji, grammar and
  cloze cards need up to four different decks. There is no default deck and no
  cloze structure — a cloze is a `standard` card by convention.
- **YouTube auto-captions repeat a rolling window of text** across consecutive
  Cues. Parsing them naively triples every word. Plan 019 merges duplicates;
  without that the feature looks broken on its most common input.
- **YouTube blocks datacenter IPs.** The caption fetch is expected to fail on
  Render. That is designed around (upload is first-class), not a bug to chase.

## Open questions, not yet settled

These were put to the maintainer during the grilling pass and the wave's plans
adopt the recommended answer. Each is cheap to reverse **before** its plan runs
and expensive after:

- **TTS**: ADR 0006 chooses browser speech synthesis over an `/api/tts` on top
  of `exam_tts.py`, to keep arbitrary user text off the 1 GB Render disk that
  exam audio lives on. No plan in this wave implements audio at all, so this is
  still fully open.
- **Mining deck targets**: plan 017 remembers the last deck per card kind in
  `localStorage` and offers to create one. An auto-created 採集 deck per kind
  was the alternative; it is a one-file change inside `useMining.js` if
  preferred.
- **Grammar chip confidence**: plan 013 applies `_distinctive` to all points,
  not just above-level ones, which is stricter than today. If legitimate points
  stop being detected, the fix is a better stem in the catalogue rather than
  relaxing the filter.

- **Rename `phrase_history` / `phrase_analysis_cache` / `/api/phrase/*` to

# Wave 5 — 解析駅, the merged analyser (2026-08-26)

Planned at commit `de78f11`, from a direct design brief rather than an audit:
*merge the phrase analyser and the video screen into one Analyzer with a
three-way source selector, and make the result beautiful, responsive and
reconciled with the app's artistic direction.*

**Frontend only.** No backend file, no schema, no endpoint changes.
`/api/phrase/*` and `/api/video/*` keep their names — `CONTEXT.md` already
records why renaming them costs a migration and buys nothing visible.

## The idea in one paragraph

`PhraseAnalyzerScreen` and `VideoScreen` do one job through two screens: take
Japanese from the world, split it into Sentences, and take each apart. They
already share `SentenceBreakdown`, `WordDetail`, `useMining` and the deep tier,
and they duplicate the rest verbatim — including the comment explaining why
`closeDetail` is a `useCallback`. `CONTEXT.md`'s own definition of **Passage**
lists typed text, a photo and a video window as one act with a `source` field.
So: **解析駅 becomes a station with three platforms** — 1番線 文字, 2番線 写真,
3番線 動画 — and the Passage it produces is drawn as a **路線図**, a line whose
stops are its Sentences, with the i+1 ones marked on the map and one stop
focused at a time. For video the focused stop is the train's position and the
線 has timestamps; for text and photo it is reading order. `次は` — the in-car
next-stop display — is how you read straight through.

## Decisions this wave embodies

These were put to the maintainer before planning and are cheap to reverse *now*,
expensive after:

- **Focused Sentence + route diagram**, not the stacked list. Chosen over
  keeping the stacked list for text/photo, and over adding an "expand all"
  toggle. The stacked list is what makes a ten-Sentence photo a wall — and it
  renders the status legend once per Sentence (`SentenceBreakdown.jsx:181`,
  `.status-legend` at 20px bottom margin), so ten Sentences print the same six
  swatches ten times.
- **The name is "Analyzer"**, American spelling, matching `t.analyze`, the
  existing codebase spelling and the `phrase-analyzer.wav` clip. The station
  keeps 解析 / KS / かいせき regardless — that is a place name, not copy.
- **The route is `/analyzer`**, with `/phrase-analyzer` and `/video` kept as
  redirects. Both have been live and may be bookmarked.
- **History stays text-and-photo.** `routes/video.py` has no index endpoint —
  only a session by id — so a unified 運行履歴 needs backend work this wave
  deliberately excludes. `AnalyzerHistory.jsx` carries a comment saying so, so
  the absence does not read as a bug.
- **One line, one colour.** 解析 keeps `--line-kaiseki` for everything

## Traps worth knowing before you start

Each is written into the relevant plan, but they are the things most likely to
cause a wrong turn:

- **CSS custom properties cannot be used in media query conditions.**
  `@media (max-width: var(--bp))` is invalid and silently does nothing. Plan 006
  therefore defines its "tokens" as a documented convention, not variables — and
  explicitly rules out adding a CSS preprocessor to work around it.
- **The theme fix must be a blocking inline script, not a React component.**
  Anything running in React runs after first paint, which is the exact flash
  being fixed. Plan 001 says so; a reviewer should check the script has no
  `type="module"`, `defer`, or `async`.
- **`useDialog`'s `onClose` must be stable.** An inline arrow re-runs the
  effect every render and makes the dialog steal focus continuously. Plan 004
  flags it at every call site.
- **Converting an element to a heading needs `margin: 0`.** Every target class
  already sets font-family/size/weight, so typography is safe — margin is the
  one UA style that leaks and visibly breaks layout. Plan 003 lists each class.
- **`animation: none` on something that fades in from `opacity: 0` leaves it
  invisible forever.** Plan 007's Step 4 exists specifically to catch this, and
  it is invisible in a diff.

## Decisions this wave embodies

- **An undo, not a confirmation dialog.** History deletion is frequent and low-stakes.
  The undo is a client-side re-create through the ordinary analyze-and-save path, because
  `DELETE /api/phrase/history/{id}` is a hard delete and adding a soft-delete column is a
  bigger decision than this wave needs. The copy says "Undo", and what comes back is the
  Passage, not the timestamp.
- **The route map keeps `role="group"` and keeps its stops as `<button>`s.** The wave-5
  audit closed a bug caused by putting a list role on them; plan 034 adds the roving
  tabindex without reopening it.
- **The kanji chip stops being the control; the character becomes it.** The chip holds a
  `MineButton`, and a `<button>` inside a `<button>` is invalid HTML with undefined focus
  behaviour. The same constraint governs the pin on a route-map stop, which is a sibling of
  the stop rather than a child.
- **No new pigment.** The 済 "already explained" mark uses shape and weight, not colour.
  The wave-5 rule holds: `--line-kaiseki` for everything structural, `--line-douga` spent
  on the timestamp chip and nothing else.
- **Audio is the browser's, per ADR-0006.** No backend TTS endpoint, no edge-tts for study
  text, no disk. The control hides itself when the platform has no Japanese voice, which
  the ADR requires by name.
- **The Sentence bank is one table with a flag, not two tables.** A kept Sentence and a
  history row store the same thing — text plus provenance, per ADR-0002 — and differ only
  in whether the learner chose it.
- **The two histories stay in two tables; the merge is a client-side view.** A Passage of
  typed text and a parsed video Track are genuinely different rows with different
  lifecycles.

## Traps worth knowing before you start

- **A `<button>` inside a `<button>` is the recurring hazard in this wave.** It bites in
  `TokenCard`'s kanji chip (plan 033) and on the route-map stop (plan 039). Both plans
  carry `container.querySelectorAll('button button').length === 0` as a required assertion,
  and both say to verify that assertion fails against a deliberately nested control.
- **`useSyncExternalStore` needs a stable snapshot.** Plan 036's voice-availability hook
  must return a boolean, never the voices array, or it loops. `hooks/useMediaQuery.js` is
  the exemplar.
- **`getVoices()` returns `[]` on Chrome's first call** and populates asynchronously via

  page load and the audio control never appears.
- **`analyze_local` is pure and must stay that way.** Plan 035's fix for the lost cue times
  belongs in the route that owns the cue data, not in the analysis module. Its own comment
  says why: *"that purity is what lets one Sentence's analysis be computed once and shared
  across every learner who asks about it."*
- **A 202 is a success and `apiJson` resolves on it.** Unchanged from wave 5, and the
  polling test is still its only guard.
- **The polling test's `apiFetch` mock must be a real resolved `Response`.** A bare
  `vi.fn()` there broke all four cases once already, for a reason unrelated to polling.
- **`video_sessions.sentences` must never be selected by a listing.** Plan 040's test 3 is

- **Baselines at planning time**: frontend 92 tests, lint 0 errors / 17 warnings, build

## The idea in one paragraph

## Decisions this wave embodies

- **The exam pipeline is deliberately NOT reused for placement.** Its papers
  are one-level, globally immutable, FK'd by attempts, LLM-generated behind a

## The diagnosis

Three mechanisms, measured rather than asserted. The colour layer
(`index.css:20-310`) is healthy and was left alone.

1. **No scale existed for anything but colour.** 94 `font-size` literals
   resolving to ~78 computed px values for about nine real sizes; 236 `padding`
   declarations, 130 used exactly once; 42 `gap` values; `border-radius`
   literals outnumbering the radius tokens 115 uses to 20; 24 `letter-spacing`
   values. `13px` and `0.8rem` are the same size written two ways, and that
   px/rem split repeats at every rung of the type scale.

2. **The direction was written nowhere.** `CLAUDE.md` — loaded into every
   session — briefed on backend layout, data flow and deployment, and said
   nothing about the station metaphor, the pigment rules or the bilingual
   pairing. `CONTEXT.md` delegates design to `docs/adr/`, and no ADR covered
   visual design. Every session therefore reconstructed the look from whichever
   file it happened to open. **This is the root cause**, and plan 043 step 4 —
   wiring `DESIGN.md` into `CLAUDE.md` — is the single highest-leverage line of
   the whole wave.

3. **The file split accelerated it, via a specific mechanism.** With no global
   spacing scale to reach for, each new stylesheet invented its own:
   `analysis.css` gained `--anl-gap` / `--anl-pad-block` / `--anl-pad-inline` /
   `--anl-radius` on 2026-08-27, and `onboarding.css` gained `--card-pad-x` /
   `-y` / `-top` on 2026-08-28. Two features, two days, two parallel design
   systems.

**But merging alone would have made one class of bug worse.** `.ember` is
declared three times at identical specificity inside the *already-merged*
`index.css`, by StageFootlights and CardStamp, and there are ~44 duplicate
selectors in that one file. Merging fixes cascade *unpredictability*; it does
nothing for *name collisions*. Hence 042 (namespacing) and 044 (a
`no-duplicate-selectors` rule) are not optional extras — they are what stop the
merge from trading one failure mode for another.

## Decisions confirmed with the maintainer up front

1. **The scales are approved as derived.** Eight type rungs, nine spacing
   rungs, six radii, four tracking values — every rung a value a reference
   screen already uses. Validated: 73 declarations already sit exactly on a
   rung, and the largest px clusters land within 0.2px of their rem twin
   (`13px` x74 to `0.82rem`, +0.12px; `15px` x37 to `0.95rem`, +0.2px;
   `20px` x8 and `40px` x4 land exact). The spacing scale deliberately is
   **not** a 4px grid, because the app is not on one — 22px, 26px and 44px are
   real load-bearing values and forcing a grid would move everything.
2. **The density contract stays.** It is the one rule in `DESIGN.md` that is a
   correction to the app rather than a description of it, and it is expected to
   fail on existing screens. That is the point.
3. **The cosmetics block stays as-is.** It repurposes nine line pigments and
   two state colours as user-selectable papers, seals and backdrops. It breaks
   "one line, one colour" on paper, but it is an opt-in decorative layer with
   its own coherent system. Recorded in `DESIGN.md` as a *standing, deliberate
   exception* with an explicit "do not cite this as precedent" note.
