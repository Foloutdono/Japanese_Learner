# Wave 3 — Sentence analysis (2026-08-26)

A **feature** wave, not an audit wave. Written from an approved design for
rethinking the phrase-analysis mode, plus a grilling pass that produced
`CONTEXT.md` (shared vocabulary) and six ADRs under `docs/adr/`. Planned at
commit `d4911a6`.

Everything above this line is the completed UI/UX work (plans 001-011). This
wave is independent of it.

## The idea in one paragraph

The phrase analyzer costs one LLM call per sentence and shows nothing without a
provider — while the backend already owns a morphological analyzer, a 205-point
levelled grammar catalogue, a JLPT difficulty grader and per-kanji furigana
alignment, none of which it uses. Everything except the contextual gloss and the
prose explanation is computable **locally, instantly, free**. Splitting analysis
into a local tier and a paid deep tier is what makes three new things
affordable: an analyzer that answers instantly, a photo of a page, and a
YouTube video's subtitles.

## Traps worth knowing before you start

- **`analyze_local` must stay pure** — no database, no `user_id`, no `core/`
  imports. That is what lets one analysis be cached and shared across every
  learner. Per-user SRS state is attached separately, at read time.
- **Token offsets are load-bearing.** Four screens render highlights, ruby,
  click targets and cloze blanks from them. Plan 013's offset-contiguity test is
  the guard; an off-by-one there is a visible defect everywhere.
- **Off-deck is not unknown.** A word in no app deck (proper noun, JMdict-only,
  slang) is something the app cannot teach, not something the learner failed to
  learn. Counting the two together would make every photo and every video
  caption look impossible and would make the i+1 signal permanently false.
- **`add_app_cards` skips rather than errors**, by design
  (`backend/routes/decks.py:868`). It returns `{"added": n}` where `n` can be
  less than what was sent. Any UI on top of it must read the count.
- **A deck holds exactly one structure**, so mined vocab, kanji, grammar and
  cloze cards need up to four different decks. There is no default deck and no
  cloze structure — a cloze is a `standard` card by convention.
- **YouTube auto-captions repeat a rolling window of text** across consecutive
  Cues. Parsing them naively triples every word. Plan 019 merges duplicates;
  without that the feature looks broken on its most common input.
- **YouTube blocks datacenter IPs.** The caption fetch is expected to fail on
  Render. That is designed around (upload is first-class), not a bug to chase.

## Open questions, not yet settled

These were put to the maintainer during the grilling pass and the wave's plans

and expensive after:

- **TTS**: ADR 0006 chooses browser speech synthesis over an `/api/tts` on top
  of `exam_tts.py`, to keep arbitrary user text off the 1 GB Render disk that
  exam audio lives on. No plan in this wave implements audio at all, so this is
  still fully open.
- **Mining deck targets**: plan 017 remembers the last deck per card kind in
  `localStorage` and offers to create one. An auto-created 採集 deck per kind
  was the alternative; it is a one-file change inside `useMining.js` if
  preferred.
- **Grammar chip confidence**: plan 013 applies `_distinctive` to all points,
  not just above-level ones, which is stricter than today. If legitimate points
  stop being detected, the fix is a better stem in the catalogue rather than
  relaxing the filter.

## Findings considered and rejected

- **Rename `phrase_history` / `phrase_analysis_cache` / `/api/phrase/*` to
  match the new Sentence vocabulary**: costs a migration and a coordinated
  frontend change for zero user-visible benefit. `CONTEXT.md` records the split
  instead — new code says Sentence, existing names stay.
- **Consolidate the eight scattered `CREATE TABLE IF NOT EXISTS` sites into one
  schema module**: tempting while fixing 020, but it risks the startup FK
  ordering that `decks.py:335` records as already resolved once. Not worth it
  for tidiness.
- **`manga-ocr` server-side**: materially the best Japanese OCR, and a ~440 MB
  model against an instance whose 1 GB disk is committed to exam audio. Rejected
  on infrastructure, not on merit — revisit if the backend ever moves. See ADR
  0004.
- **Self-hosted ASR for videos with no caption track**: does not fit the
  instance, and neither configured provider transcribes audio. A paid ASR API is
  a real option but is an operator decision with a per-minute cost, so it needs
  its own plan. See ADR 0003.
- **Raising `_call_llm`'s `max_tokens=1200`** to handle pasted paragraphs: the
  cap is a documented choice (`backend/routes/phrase.py:172-183`). Multi-sentence
  input is solved by splitting the Passage, never by asking for a bigger answer.

## Traps worth knowing before you start

Each is written into the relevant plan, but they are the things most likely to
cause a wrong turn:

- **CSS custom properties cannot be used in media query conditions.**
  `@media (max-width: var(--bp))` is invalid and silently does nothing. Plan 006
  therefore defines its "tokens" as a documented convention, not variables — and
  explicitly rules out adding a CSS preprocessor to work around it.
- **The theme fix must be a blocking inline script, not a React component.**
  Anything running in React runs after first paint, which is the exact flash
  being fixed. Plan 001 says so; a reviewer should check the script has no
  `type="module"`, `defer`, or `async`.
- **`useDialog`'s `onClose` must be stable.** An inline arrow re-runs the
  effect every render and makes the dialog steal focus continuously. Plan 004
  flags it at every call site.
- **Converting an element to a heading needs `margin: 0`.** Every target class
  already sets font-family/size/weight, so typography is safe — margin is the
  one UA style that leaks and visibly breaks layout. Plan 003 lists each class.
- **`animation: none` on something that fades in from `opacity: 0` leaves it
  invisible forever.** Plan 007's Step 4 exists specifically to catch this, and
  it is invisible in a diff.

- **Plan 004's first pass left one live focus-steal bug in `QuickChange.jsx`
  (2026-08-25)**: the executor correctly stabilized `onClose` at 5 of 6 dialog
  call sites (and caught 3 extra sites outside the literal scope list that
  needed the same fix), but `QuickChange.jsx:50`'s
  `<QuickDrawer onClose={() => setOpen(false)} .../>` was left as an inline
  arrow. Traced through source to a real, repeating bug: `QuickDrawer`'s
  `equip()` calls `equipCosmetic()` → `refreshSummary()` → the
  `profileSummary` store's `listeners.forEach` → every mounted
  `useProfileSummary()` consumer re-renders, including `QuickChange` itself —
  so every single cosmetic equip inside the open drawer recreated the inline
  `onClose`, gave `QuickDrawer`'s `close` a new identity via its own
  `useCallback([onClose])`, and re-fired `useDialog`'s focus-on-open effect,
  yanking keyboard focus back to the first control mid-interaction. Sent back
  as REVISE with the exact fix (mirroring the `useCallback` pattern already
  correct in `BurgerMenu`/`DeckDetailScreen`/`ReadingScreen`); executor applied
  it in one commit, re-ran the full gate, confirmed scope stayed to that one
  file. Verified independently before merge — the fix is mechanical
  (`useCallback(fn, [])` has a permanently stable identity by React's
  contract) rather than live-tested, since this environment has no path to an
  authenticated session for browser verification. Worth remembering for any
  future `useDialog`-style hook: the stability requirement applies transitively
  through every wrapping `useCallback` up to the actual `<Component open={...}
  onClose={...}>` call site — checking only the immediate call site inside the
  dialog component itself is not enough.
- **Plan 004 also surfaced an untracked-to-tracked drift in `plans/` itself**:
  between the plan 003 merge and the plan 004 dispatch, `plans/` was committed
  to git as tracked content (commit `955b351`, message
  "feat(a11y): add plan 007...") — not something done as part of this advisor
  session's own actions, which had deliberately kept `plans/` untracked
  throughout. Left as-is (benign content, doesn't touch source) rather than
  reverted, but flagged to the operator rather than silently absorbed.
- **Plan 005's Step 4 mouse-check wording was wrong for text fields
  (2026-08-25)**: the plan asserted "`:focus-visible` excludes mouse focus in
  every current browser" and treated a ring appearing on mouse click as a
  STOP condition. The executor found, and the coordinator independently
  reproduced with a real (non-synthetic) mouse click, that this is false for
  text-editable elements specifically: `input[type=text/email/password]`,
  `textarea`, and contenteditable are spec-permitted (CSS Selectors Level 4)
  to always match `:focus-visible` on click in every evergreen browser,
  because a focus indicator is considered useful right before typing
  regardless of input modality. It does **not** apply to non-text controls —
  the existing `button:focus-visible` house pattern was verified to still
  correctly suppress the ring on mouse click, confirming the CSS added by
  plan 005 (`input:focus-visible`, `textarea:focus-visible`,
  `.import-textarea:focus-visible`) is correct as written and not a defect.
  This is a flaw in the plan's own Step 4 wording, not in the executed work —
  the outcome (a legible, spec-compliant ring on text fields on click too) is
  arguably a feature, and there is no better alternative selector (`:focus`
  would be strictly worse; detecting "keyboard-only" needs JS). Worth
  remembering for any future plan writing a mouse-vs-keyboard STOP condition:
  scope the "`:focus-visible` excludes mouse" claim to non-text-editable
  controls only.

  `PhraseAnalyzerScreen.jsx`, `ReadingScreen.jsx` — `mode_*`/`theme*`/
  `volume*`/`interval*`/`field_*`/`status_*` prefixes only, none matching
  these 8 names). Deadness re-established accounting for all of them, and the
  8 keys were **deleted in plan 011**, which also added a locale-parity test
  (`frontend/src/locales/locales.test.js`) so a future one-sided key add fails
  `npm test` immediately instead of silently drifting. Keep this dynamic-site
  list current if a new one appears.
- **The ~40 `t.X ?? 'literal'` fallback sites**: audited by resolving every key
  against both locale tables. Only **two** ever actually fire, and both are
  fixed by plan 002. The rest are dead defensive code. Removing them is a
  cosmetic cleanup, not a fix.
- **`min-width: 900px` / `max-width: 900px` both matching at exactly 900px**:
  looked like a classic off-by-one breakpoint conflict. It is not — they target
  disjoint selectors (`.syllabary-chart-group` vs `.grid-4`/`.grid-3`) and never
  interact. Plan 006 says to leave both alone.
- **`max-width: 1099px` / `min-width: 1100px`**: a correct complementary pair
  written with integer pixels so they never overlap. Deliberate, not drift.
- **14 `<div onClick>` sites**: these are modal scrims implementing
  click-outside-to-close, which is a standard pattern. The real problem is the
  missing Escape handling and focus management, which is plan 004 — the `div`
  itself is not a finding.
- **Two `outline: none` sites at `index.css:7940` and `:8886`**: both have
  working alternative focus indicators (a seal skin that draws its own, and a
  `:focus-within` background change on the wrapper) and both carry comments
  saying so. Plan 005 explicitly excludes them.
- **"The login form has no focus indicator at all"**: this was an initial
  reading during the audit and it was **wrong** — a measurement artifact from
  probing a browser pane that did not have window focus, so `:focus` did not
  match. The accurate, narrower finding (a 1px border-colour change on `:focus`
  rather than the app's 2px `:focus-visible` house ring) is what plan 005
  addresses. Recorded here because the wrong version is the more alarming one
  and would otherwise get "re-found".
- **109 `transition:` declarations**: not audited for reduced-motion. Nearly all
  are short colour/hover transitions with no vestibular risk. Plan 007 scopes
  itself to `animation` and notes this as a deferred targeted pass.
- **`frontend/src/exam/exam.css` (892 lines)**: only spot-checked (its
  breakpoints are all `560px`, so no migration needed). Not audited for focus
  handling or motion. Worth a follow-up pass — the exam is a timed flow where
  keyboard use is likeliest.

## Not audited in this pass

Scoped out because this was a UI/UX-focused audit of `frontend/`:

- The entire `backend/` tree — covered by the previous backlog's 11 plans.
- Colour contrast ratios. The app has nine cosmetic "paper" themes that change
  surface colours, so a real contrast audit means checking every foreground
  against nine backgrounds in two themes. Genuinely worth doing; genuinely its
  own project.
- Touch target sizes. Spot-checked, and a handful of controls sit at 34×34px
  under the 44×44 guideline — but they are all icon buttons with adequate
  padding around them, and confirming whether that padding counts requires
  measuring live rather than reading CSS.
- The study-loop UX itself (card flow, rating, session pacing) — the actual
  product design, as opposed to its accessibility and shell. A different kind of
  review.

## Direction (options, not problems)

Surfaced during the audit; not turned into plans because they are the
maintainer's call, not defects:

- **The design language exists only in code comments.** The station/railway
  metaphor — 駅名標 plates, departure boards, 改札 gate, 車内案内表示器 — is
  documented in genuinely excellent code comments and nowhere else. Those
  comments show it being re-derived repeatedly ("which is exactly why they read
  as imported from another design"). A `DESIGN.md` would turn re-derivation into
  reference — and would make plans like 003 and 006 much easier to write next
  time, since both spent their effort reconstructing intent that already exists.
- **A token/component gallery on the existing dev route.** 518 CSS custom
  properties with no inventory. `RewardsPreview` already exists as a dev-only
  workbench at `/dev/rewards`, with the `import.meta.env.DEV` tree-shaking
  pattern established. Extending it into a swatch and component gallery is
  maybe a day and would make breakpoint and token drift self-evident rather than
  something an audit has to go find.
